2 Background
The following background distinguishes metamorphic rewriting from polymorphic en-
coding and introduces the transformation families used in the baseline evaluation.
2.1 Metamorphic Engines
A metamorphic engine constructs a different instruction-level representation of an input
program intended to preserve its behavior. Early virus generators used this idea to vary
their byte sequences between instances [25]. Functional preservation is a design objec-
tive and must be checked; it does not follow merely from the fact that a transformation
has produced an executable output.
A key difference is the absence of a mandatory decrypt-and-execute stage [29]. An
encryptedpayloadisnormallyrecoveredbeforeexecution,whileasuccessfullyrewritten
payloadcanexecuteinitstransformedrepresentation.Thischangeswhatamemoryscan
may observe, without implying that the transformed program is undetectable.
Instructionsubstitution,insertion,andreorderingcangeneratemanyrepresentations
from the same input [29,17]. This diversity complicates the use of fixed byte patterns,
and places a substantial burden on the rewriting engine to preserve control flow, data
references, and processor state. Transformation-based evasion and its limitations are
surveyed in [12].
Comparison with Polymorphism. Polymorphic encoding usually combines an encoded
body with a variable decoding routine [25]. Shikata Ga Nai is a representative example:
variation in its decoding stub changes the static byte sequence, but recurring features of
that stub can themselves be used for recognition [18]. Once decoding has completed,
the original body may be available to memory analysis. Metamorphic rewriting instead
changes the body that is executed [11]; this is a distinction between representations, not
a guarantee of runtime evasion.
2.2 Morphing Techniques
The established transformation families considered in Zone are EQ, NOP insertion,
IBP, and BCF. They can be evaluated separately or in selected combinations. Their an-
tecedents are discussed in Section13.

EQ changes the instruction vocabulary; NOP insertion adds operations intended to
leave the relevant computation unchanged. IBP modifies the physical layout of instruc-
tionblocks,whereasBCFintroducesbranchesandunreachableregions.PII,describedin
Section 3.1, further separates instruction placement from logical execution order. These
descriptions summarize the design reported in [4].
Equal Code Substitution. EQ replaces an operation with an alternative representation
intended to have the same effect. For example, the zeroing operationsXOR rax, rax
and MOV rax, 0x0 have different encodings. Such examples illustrate changes in byte
representation; preservation of all relevant state remains an implementation concern.
Table 1 collects the substitution examples used in the conference study, including
arithmetic complements and stack-based sequences. Instruction substitution and its use
with insertion transformations have a long history [7,8,23].
NOP/Dead Code Insertion. Insertion transformations introduce operations intended to
leave the program’s relevant behavior unchanged. The single-byteNOP is one example;
Table2 reproduces the other examples considered in the original implementation.
Some apparent no-ops, including arithmetic with zero, can change processor flags.
The original implementation therefore used flag-preserving sequences around such op-
erations,asillustratedinTable 3.Theresultingrepeatedpatternsarethemselvesrelevant
to detection: changes introduced by an engine can create recognizable regularities [3].
Instruction Block Permutation. IBP changes where instruction blocks are stored while
retaining their intended logical succession. The original implementation organizes the
transformation into the following stages:
1. Partitioning.The instruction sequence is divided into blocks; the chosen granular-
ity affects both rewriting overhead and the amount of layout variation.
2. Connecting blocks.An unconditional branch links each block to its logical succes-
sor.
3. Changing placement. Blocks are permuted, while the entry block retains its posi-
tion.
4. Updating references.Control-flow targets are adjusted to the resulting layout.
This transformation changes adjacency without necessarily changing most instruc-
tions within a block. Consequently, a detector based on a short pattern internal to an
unchanged region may behave differently from one that relies on a longer contiguous
sequence. The experiment assesses these changes empirically rather than assuming that
every signature is disrupted.

3.1 Position-Independent Instruction
PII was introduced in the conference paper [4]. It decouples the physical position of an
instruction from its place in the intended execution sequence.
Organization. Consider an instruction such asADD rax, 1 . In the PII representation
it is placed in a wrapper rather than relying on adjacency to its successor. The wrapper
executes the original operation and transfers control to a redirector. An offset table sup-
plies the location of the next logical instruction. Figure1 reproduces the overall layout,
while the listings below document the components of the original design.
The representation consists of four components:
1. Base-Address Stub (Stub1). This component determines the runtime base address
and records it in a designated memory location.

PAGE 7

2. Redirector Stub (Stub2). This component obtains the next logical instruction lo-
cation from the offset table and dispatches execution to it.
3. Offset Table.Thiscontiguoustablecontainstheinstructionoffsetsusedbytheredi-
rector.
4. Wrapped Instructions. Each input instruction is placed in a wrapper intended to
maintain the required register, flag, and stack state.
Execution Sequence. The conference paper describes execution in three phases:
– Initialization. A call enters Stub1 (Listing1). The return address supplied by that
call is used to establish the payload’s runtime location.
– Original operation. The wrapper in Listing2 restores the saved state, adjusts the
stack, executes the input instruction, and supplies its logical index to Stub2.
– Dispatch. The redirector in Listing3 saves the state it uses, obtains the successor’s
location from the offset table and base address, and transfers control to that wrapper
after restoring the relevant state.
Physical Placement. The original implementation permutes complete wrappers, treat-
ing each five-instruction wrapper as a unit. The offset table is updated for the resulting
placement. Execution still starts with the initial call to Stub1; logical succession is rep-
resented by the table rather than by the wrappers’ physical adjacency.

3.2 How Instructions Are Patched
Moving instructions or inserting bytes can invalidate references to their previous loca-
tions.Thepatchingphaseupdatescontrol-flowdestinationsandotheraffectedreferences
tothemodifiedlayout.Branchesandcallsarethereforepartoftherewritingprocess,not
merely instructions that can be copied without regard to their new positions.
This requirement also explains the scope restriction. Rewriting raw instruction se-
quences already requires consistent target updates; complete PE files introduce addi-
tional metadata and layout dependencies. Algorithm1 reproduces the high-level work-
flow from [4].
3.3 Transformation Pipeline
The original workflow in Algorithm1 can be read as six stages. The additional analysis
and transformation paths are described in Sections8–10.
1. Input representation. Capstone produces instruction objects held in a linked se-
quence, with an address-indexed dictionary for lookup (Line4).
2. Embedded data. The implementation enables Capstone’s Skipdata option
(Line 5). This does not solve the general problem of identifying inline data,
particularly when data bytes also admit an instruction interpretation [10].
3. Reference tracking. A label table associates each tracked control-flow operation
with its target instruction object. This association is retained as the object’s physical
address changes.
4. Transformation and layout update. The chosen transformations are applied
(Line 19), followed by recomputation of instruction addresses (Line12).
5. Reassembly of tracked branches.Keystoneassemblesthetrackedcontrol-flowop-
erations using their updated targets (Line25).
6. Output. The resulting instruction bytes are written as a new raw binary (Line36).

6.1 Mitigations and Countermeasures
Changing the binary representation does not remove a program’s observable actions.
Defensive analysis can consider memory protections, execution patterns, API activity,
and network behavior in addition to static bytes. Recognition of a transformation engine
is another possibility: repeated artifacts of a common toolchain can persist across out-
puts, as documented for Shikata Ga Nai [18]. Statistical or learned detectors must also
account for benign programs that share similar features. These are defensive considera-
tions arising from the study, not results of an additional detection experiment.
7 Comparison with Shikata Ga Nai
The conference paper [4] compared Zone with the Shikata Ga Nai (SGN) polymorphic
encoder[13].SGNcombinesadditive-feedbackencodingwithavariabledecodingstub.
The comparison included the original x86 encoder and an unofficial x64 implementa-

– x86: SGN had a10.22% detection rate, while Zone achieved0.25% (also reaching

8.1 Problem and Representations
For an input byte sequence𝐵 = (𝑏0, . . . , 𝑏𝑛−1), identification returns candidate data
intervals[𝑠 𝑗 , 𝑒 𝑗) in payload-relative coordinates, with optional kinds such as ASCII,
UTF-16LE, or another data object. Acceptance for rewriting additionally depends on
referenceevidenceandimplementationsupport.Theoriginalinline-dataandimmediate-
operand examples in Tables5 and 6 motivate this added layer.
The implementation distinguishes a model’s reported intervals, regions accepted by
deterministic checks, and regions actually extracted. These sets need not coincide. An
unsupported reference can prevent processing of a correctly identified object, while fil-
tering can make different proposals yield identical final binaries. Evaluation retains the
output stage associated with each observation.
8.2 Symbolic and Heuristic Identification
Thenon-LLMpathcombinesCFGFastcandidateblocksandinferreddatawithbounded
symbolic exploration. Observed instruction starts are expanded into their decoded byte
spans, and newly observed entries can seed a further graph-recovery pass. This prevents
interior bytes of an observed instruction from being treated as unvisited data solely be-
cause only its start address was recorded.
The initial state leaves uninitialized registers and memory symbolic; it does not
reproduce a complete Windows process or all API behavior. Time, state/block-step,
pending-state, and solver limits bound the analysis. Reports record termination reasons,
unresolved states, and errors. Missing observations therefore do not prove that a region
is data or unreachable.
Printable ASCII and UTF-16LE patterns supply additional candidate evidence. Ob-
served code spans prevent their acceptance under the string heuristic. For strings over-
lapping candidate graph code, additional structural corroboration is required. Graph-
inferred data and bytes outside recovered blocks retain different evidential categories;
thelatterareuncertainratherthanacompletedatapartition.Theavailableanalysislimits
and candidate categories accompany the classification result.

9.3 Validation and Independent Functional Assessment
Structural checks cover assembly, decoding coverage, tracked control flow, data consis-

10 Integration of Assembly Wrapping
10.1 Existing Technique and Implementation Scope
Assembly wrapping is an existing technique based on alternative instruction interpreta-
tions [1]. The contribution here is its integration into Zone and empirical assessment.
The instruction view obtained by static decoding can differ from the stream followed
during execution; representation measurements must state which view they use.
The implementation now supports both x64 and x86. The x86 path was added af-
ter the first benchmark snapshot and is assessed against a separately identified version.
Registerwidth,instructionencodings,andaddressingrequirearchitecture-specifictreat-
ment; an x64 outcome is not transferred to x86 by assumption.
10.2 Integration and Assessment Boundary
Wrapping depends on an adequate instruction interpretation, data preparation, and con-
sistent handling of supported references. Some regions may remain outside the main
wrapped representation, and construction may be refused on unsupported inputs. Avail-
ability, construction success, empirical functionality, size, and diversity are therefore
distinct outcomes.
The benign x64 and x86 fixture results and the separate 102-payload campaign ap-
pear in Section12. The latter includes unbuilt and non-working outputs. Functional re-
sults on the curated fixtures are not used as evidence of universal payload support. The
olderselectedx64wrapping/static-scancohort isalsoidentifiedseparately,includingits
construction failures and duplicate outputs.

13 Related Work
Instruction-level obfuscation has been studied in both offensive and defensive set-
tings[26,6].Earlierengines,includingW95/Regswap[ 8]andMetaPHOR[ 24],explored
register substitution and code reorganization. Instruction substitution, insertion, and
control-flow transformations underpin the techniques summarized here [7,8,23,10,15].
Polymorphic encoding provides a related but distinct representation strategy. Anal-
yses of SGN describe both the variation in its decoding stub and opportunities to recog-
nize it [9,18]; memory-extraction research addresses the body recovered during execu-

26 S. Bistarelli et al.
tion[11].Formetamorphicprograms,detectionstudieshaveconsideredHiddenMarkov
Models [27,8], API-trace similarity [29], and genetic-algorithm-based methods [14].
More recent work examines LLM-based assembly transformation, including the
MetamorphASM benchmark and its MAD dataset [19,16]. Compiler-based systems
such as Obfuscator-LLVM [15] offer another setting, with access to source-level or
intermediate information during compilation.
The contribution of the conference paper was its payload-levelbin2bin study, the
PII design, and the joint evaluation of selected transformation configurations [4]. Those
contributions are the starting point of this manuscript, rather than new claims of the
extended version.
The extensions additionally connect data identification with bounded symbolic
and static analysis [2], and distinguish LLM classification from assembly transforma-
tion. Assembly wrapping is attributed to its existing description and acknowledged
antecedents in overlapping instructions [1]; its integration into Zone is assessed as an
implementation contribution. These new directions build on the earlier payload-level
study while preserving its detailed results for comparison.
14 Conclusions
The original Zone design and its 102-payload evaluation remain the foundation of this
extended study. Their detection, working-rate, size, entropy, and similarity observations
show why representation change and empirical functionality require separate measure-
ments. The PII design and historical SGN comparison are retained within their original
experimental boundaries.
The extensions add explicit code–data identification, LLM-assisted transformation,
andwrappingforbotharchitectures.Independentannotationsonsixcuratedfixturesgive
exact identification in 18/18 LLM and 6/6 symbolic runs. The benign transformation
experiments produce accepted outputs with correct buffers in 167/168 x64 and 138/144
x86invocations,underdifferentfrozenversions.Theseresultsareboundedbythefixture
oracle and do not establish universal semantic preservation.
Thebroaderwrappingcampaignbuilds243/306variantsandpasses170/306harness
checks, despite complete wrapping success on the small benign corpus. On nineteen
selected real payloads, final-output identity and reported range agreement also differ.
Together these observations expose the limits of extrapolation from curated tests and
theneedtoseparateclassification,construction,andexecution.Completedraw-filescans
characterize a separate earlier cohort; the ongoing full-payload DeepSeek and current
scan campaigns remain incomplete at the declared cutoff. Their final outcomes must be
assessed with their own versions, budgets, and denominators.
