Abstract. Binary metamorphism depends on recovering executable instructions
while preserving embedded data and the references that connect them. This
article extends Zone, a binary-to-binary rewriting engine for compact Windows
x86 and x64 payloads, with code–data identification and LLM-assisted trans-
formation. One identification path combines bounded symbolic exploration,
control-flow recovery, and complementary heuristics; another uses an LLM to
propose data ranges for a shared deterministic data-handling layer. A separate
LLMpipelinetransformsassemblyusingfourestablishedtransformationfamilies
and supports zero-shot and two-shot prompting. The extension also integrates
assembly wrapping, an existing technique, with an x86 port under development.
The assessment distinguishes classification quality, build success, empirical
functionality, static-scan verdicts, representation similarity, output diversity,
and generation cost. The conference experiments provide a separately identified
historical baseline. This separation permits analysis of which conclusions follow
from classification, validation, and execution evidence, and which require further
investigation.

challenge for malware analysis [11,5,18]. A useful assessment must establish what was

Motivation. A sequence of bytes can be both a valid instruction encoding and part of
a string or another data object. Successful decoding therefore provides insufficient evi-
dence that the bytes should be rewritten as instructions. The conference study identified
this ambiguity as a source of functional failures. Addressing it requires more than a
different transformation: the engine must identify candidate data, preserve its contents,
and maintain the references through subsequent layout changes. Failures at any of these
stages can invalidate an otherwise well-formed output.
LLMs introduce two further questions. They can be used to classify regions of a
binary, and they can be asked to transform an assembly representation. The first task
produces candidate labels or intervals; the second produces a new instruction sequence.
They have different outputs, validation requirements, and failure modes. We conse-
quently study them as separate components, even though both interact with the same
data-handling infrastructure.

2 Background and Related Work
2.1 Metamorphism and Binary Rewriting
Metamorphic transformation changes the program body rather than merely changing an
encoded copy and a decoder. Earlier engines explored register substitution, instruction
replacement, and code reorganization; their development and detection are discussed
in [21,6,7,20]. Surveys place these approaches within the broader space of obfuscation
and malware transformation [22,4,11].
Zone uses four established transformation families in addition to PII. Equal code
substitution (EQ) changes the instruction representation of an operation. NOP insertion
adds operations intended to leave relevant state unchanged. Instruction block permu-
tation (IBP) changes the physical order of blocks while retaining their logical succes-
sion. Bogus control flow (BCF) adds paths with predetermined outcomes and regions
excluded from the intended execution. These names describe transformation goals; cor-
rectness depends on the treatment of flags, registers, memory, and control-flow refer-
ences in each implementation.
Compiler-based obfuscation, exemplified by Obfuscator-LLVM [14], operates with
intermediate representations and information unavailable to a raw-binary rewriter. Na-
tive binary rewriting must first recover the instructions and references that it will mod-
ify [9]. This difference is central to the code–data problem examined here.
2.2 Code–Data Identification
A disassembler assigns an instruction interpretation to byte sequences; that interpreta-
tion need not reflect the role of the bytes during execution. Linear decoding can traverse
embedded strings, whereas control-flow recovery can miss paths that depend on unre-
solvedvalues.Thedifficultiesofrecoveringcontrolflowfrombinarieshavebeenstudied
beyond the payload setting [24].
The angr framework exposes static control-flow recovery and symbolic execution
as distinct forms of analysis [2]. The former provides candidate blocks; the latter can
provide evidence of addresses visited under a model and resource budget. Missing envi-
ronmental behavior and incomplete exploration limit both the recovered graph and the
interpretation of unvisited addresses. The identification layer in this article combines
these sources of evidence with explicit heuristics. It does not equate an unvisited byte
with a proven data byte.

2.3 LLMs for Assembly Analysis and Transformation
Prior research has investigated LLM-generated metamorphic variants and assembly-
level obfuscation, including the MetamorphASM study and its evaluation set-
ting [15,17]. Such work motivates examining model outputs as structured artifacts
that require assembly and validation. The ability to produce plausible assembly is
distinct from preserving the behavior of a particular input.
Our extension separates two applications. The identification task asks for candidate
dataranges.Thetransformationtaskasksforamodifiedassemblyprogramunderaspec-
ified transformation family. Deterministic checks surround both tasks, so the evaluated
object is a complete pipeline as well as the model’s initial proposal. The number of
examples in the first prompt and the presence of subsequent feedback are reported sep-
arately.

PIIwasintroducedintheconferencearticle[ 3].Itseparateslogicalexecutionorderfrom
the physical placement of instruction units. The published representation uses wrapped

later implementation revisions. It also distinguishes a dispatcher-based representation

4.2 Symbolic and Heuristic Identification
The non-LLM path combines static graph information with bounded symbolic explo-
ration. A CFGFast pass supplies candidate code blocks and inferred data objects. Sym-
bolic explorationrecords instruction addresses visited under the raw-payload model. An
additional graph-recovery pass can use newly observed entries, so that dynamically ob-
served code is not lost merely because it was absent from the first graph.
The symbolic initial state models uninitialized registers and memory symbolically.
It does not initialize a complete Windows process or implement all external API behav-
ior. Exploration is bounded by a time budget, a state/block-step limit, a pending-state
limit, and solver budgets. Reports record the stop reason and unresolved states. Reach-
ing a resource limit, encountering an unsupported operation, and exhausting the current
frontier have different meanings and are reported separately.
The implementation maintains evidence at byte granularity by expanding observed
instruction starts into their decoded spans. This avoids treating the interior bytes of an
observedinstructionasunexecuteddatacandidates.Candidatestringsarethenidentified
withprintableASCIIandUTF-16LEpatterns,includingtheirterminators.Overlapwith
observed code prevents acceptance under this string heuristic.
Static graph recovery can itself classify a string as code. For a string that overlaps
candidate graph code, the implementation requires additional structural corroboration
rather than relying on printability alone. Other proposed regions originate from graph-
inferreddataorfrombytesoutsiderecoveredblocks.Thelatterremainuncertainandare
distinguished from stronger data candidates.
The analysis returns intervals, their kinds, and diagnostic information; it does not
prove a complete partition of the payload into code and data. In particular, a byte not

4.3 LLM-Based Identification
The alternative identification path presents the input through a hex view, a linear disas-
sembly, and candidate printable runs. These are different views of the same bytes. The
disassembly is explicitly heuristic, and the printable runs are candidate evidence rather
than reference labels. The model returns structured data ranges, including offset and
length, instead of a rewritten binary.
The parser checks that intervals have positive lengths, remain within the input
bounds, and do not overlap. The engine then associates candidate ranges with its exist-
ing reference information. Ranges that cannot be accepted by the configured pipeline
are reported or rejected. A fresh engine instance is used when applying a proposal,
avoiding reuse of partially modified state after a rejected answer.
An invalid answer can trigger another request with feedback. The reported outcome
therefore distinguishes the first proposal, later proposals, and the final accepted result.
This distinction is necessary to attribute an observation correctly: a useful final extrac-
tion may reflect both the model’s proposal and deterministic filtering.
The number of worked examples in this classification prompt is recorded indepen-
dently of the transformation experiment. A zero-shot/two-shot comparison of assembly
transformation does not imply that the same comparison has been performed for identi-
fication.

4.5 Classification Outputs and Residual Uncertainty
Three outputs are retained for analysis: raw candidate intervals, intervals accepted by
deterministic checks, and intervals ultimately processed by the data layer. Equal final
binaries do not establish equal raw classifications, because filtering can remove differ-
ences. Conversely, a correct candidate can be rejected because its reference pattern is
unsupported. That rejection is an integration limitation, not necessarily a classification
error.
The evaluation in Section7 therefore separates classification quality from down-
stream functionality. Successful execution supplies evidence about the observed behav-
iorafterdatahandling,whilereferenceannotationssupplyevidenceaboutthebyteroles.
Neither observation can substitute for the other.
5 LLM-Assisted Assembly Transformation
5.1 Task and Supported Transformation Families
The transformation path asks an LLM to produce a complete modified assembly repre-
sentation for a selected family: EQ, NOP insertion, BCF, or IBP. These families retain
their meanings from the native engine; the use of a model changes how the proposed
representation is produced. Each request selects one family so that the generated artifact
and its validation policy have an identifiable experimental condition.
PII and assembly wrapping remain native paths in the version examined here. They
arenotdescribedasLLM-generatedtechniques.Likewise,anativeconditioncombining
transformations is not automatically equivalent to several model calls in sequence. The
experiment identifies the implemented path rather than grouping all uses of the same
family under one label.
5.2 Assembly Representation and Data Boundary
The engine prepares an assembly representation with symbolic labels for the relevant
locations and preserves the data representation outside the model-generated instruction
text. This preparation defines an intermediate input to the transformation task. It also
determinesthereferencepointforseveralstructuralchecksandsimilaritymeasurements.
The model’s text is assembled and associated with the data retained by the engine.
The output is therefore a product of model generation, assembly, data handling, and
validation. The experimental record retains the identity of the original file, the inter-
mediate representation, and the final bytes, so that preparation-induced changes can be
distinguished from changes in the model’s output.
5.3 Zero-Shot and T wo-Shot Conditions
The initial zero-shot request contains the task specification without worked examples.
The initial two-shot request contains two examples in addition to that specification. The
example identities and prompt versions are part of the experimental condition. Differ-
ences in their content, not only their number, can influence the comparison.

5.4 Validation and Feedback
Validation covers several kinds of structural evidence. Assembly must succeed, the pro-
duced code must meet the decoding checks, tracked branch destinations must have ap-
propriate boundaries, and the expected data representation must remain consistent. Ad-
ditional checks depend on the selected family and examine whether the output still con-
tains the required instruction structure or applies a nontrivial transformation.
These checks are deliberately narrower than semantic equivalence. An output can
pass structural validation yet behave differently; a conservative check can also reject an
output that would have performed the expected behavior. The assessment records the
reason for each rejection rather than treating all rejected answers as one category.
For supported test cases, a functional verifier can participate in the generation loop.
If that verifier is also used to select accepted outputs, a later test based on the same
observableisconditionalonselection.Thearticledistinguishesthispipelineacceptance
criterion from an independent functional assessment and reports attempts that exhaust
the allowed budget.
5.5 What Is Attributed to the Model
Three aspects are considered separately: whether an answer can be assembled, whether
the complete pipeline accepts it, and whether an accepted output satisfies the reported
functional check. Deterministic preparation and validation are part of the system contri-
bution rather than capabilities attributed to the model alone.
The run record includes elapsed time, API usage when supplied by the service, re-
jected attempts, and the accepted artifact. Estimated cost is derived from the stated tariff
snapshot; it is not presented as an invoice. Resumed jobs and reused outputs are identi-
fied so that they are not counted as additional generation calls.

The relevant conceptual property is that the instruction interpretation obtained by a
particular static decoding need not be the instruction stream followed during execution.
This property makes it especially important to identify which representation is used by
a similarity or coverage measurement. A statistic from the static view and one from the
intended execution view answer different questions.
6.2 Integration and Supported Inputs
Wrapping is integrated with the native rewriting infrastructure and depends on an in-
struction representation adequate for the selected input. It must also interact with the
final data layout and the references affected by changes in instruction placement. Con-
struction can be refused when the required input interpretation is incomplete or an un-
supported case is encountered.
Some instructions or local regions are handled differently from the main wrapped
representation. The assessment therefore records the proportion represented by wrap-
ping, retained regions, output size, construction failures, and functional outcomes. A
claim about the whole output must not be inferred solely from the fraction of instruc-
tions accepted by one internal stage.
The experiment distinguishes wrapping alone, the chosen combined native condi-
tion, and the corresponding preparation-only controls. Their names identify complete
configurations, including data handling and architecture. Implementation availability
and successful build are reported separately from empirical functionality.
6.3 x86 Port and Development Status
The x64 implementation is available for assessment. The x86 port is under active devel-
opment at the time of this draft. Register width, instruction encodings, and addressing
assumptionsrequirearchitecture-specifictreatment,soanx64outcomeisnottransferred
to the x86 column of a result table.
The result layout reserves separate x86 entries. Those entries remain marked as
development work until a frozen version and its assessment are available. If the port
changes during a campaign, its new results are associated with the new version; they are
not silently appended to results from an earlier implementation.
6.4 Assessment Boundary
Wrapping is assessed with the same separation of construction, functionality, and rep-
resentation measurements used for other methods. In particular, a failure to construct an
output remains part of the overall outcome. Reporting functionality only for constructed
binaries can describe accepted artifacts but does not describe availability across all at-
tempted cases. Section7 defines both denominators.

7.4 Build Success and Functional Outcomes
Let 𝑁 be the number of planned cases,𝐵 the number producing an accepted binary, and
𝑊 the number passing the stated functional check. The assessment reports
BuildRate = 𝐵/𝑁, WorkingRateall = 𝑊/𝑁, WorkingRatebuilt = 𝑊/𝐵. (3)
All three counts accompany the percentages. An unbuilt case is not removed from the
first two denominators. An incomplete or unexecuted case remains distinguishable from

The functional oracle is specified by payload class. An observed connection, an
opened port, a dialog, and exception-free termination are different observables with dif-
ferent evidential strength. The harness version, architecture, observation window, and
relevant configuration are recorded. Original inputs are checked under the same current
harness to characterize its baseline behavior.
These observations do not prove complete semantic equivalence. A connection can
occur before later execution fails; clean termination may not exercise the intended op-
eration; and a dialog verifies only the behavior observed by that test. Conclusions retain
the scope of the oracle actually used.
For LLM runs, the record additionally distinguishes initial acceptance, acceptance

9 Discussion and Threats to Validity
9.1 Identification and Integration Failures
Code–dataidentificationanddata-preservingrewritingexposerelatedbutdistinctfailure
modes. An incorrect candidate can mark code as data. A correct candidate may have
an unsupported reference. A successfully processed region may still be followed by an
incorrect transformation elsewhere in the payload. The interpretation of a working-rate
change therefore depends on the stage-level evidence.
Bounded symbolic exploration adds a specific uncertainty: an observed address es-
tablishes that the analysis visited that address under its model, while absence from the
observation set establishes much less. External Windows behavior, unresolved states,
and analysis limits can leave code unvisited. The heuristic combination and its diagnos-
tics must remain visible when interpreting the result.
For the LLM path, agreement with another method can characterize shared outputs
without resolving shared errors. Deterministic filtering can also make different raw an-
swersconverge.Reportingcandidateandacceptedstagesseparatelyisconsequentlynec-
essary for attribution.

9.2 Validation, Selection, and Measurement Bias
Static checks can reject malformed or inconsistent outputs without proving the behavior
of accepted ones. Functional checks narrow the uncertainty only to the observables ex-
ercised by the harness. A single successful action does not characterize every execution
path or future interaction of a payload.
When the same functional check is part of generation-time selection and later re-
porting, the resulting pass rate concerns selected outputs. It must be read alongside
first-attempt acceptance, exhausted runs, and the complete retry budget. Repeating a
failed run until the campaign contains an accepted artifact changes the selection process
and is retained in the record rather than hidden by the final file.
Similarity introduces another source of interpretation bias. Sequence matching un-
der normalization, frequency-vector cosine similarity, and byte identity quantify differ-
ent relationships. Pooling programs into one frequency vector also changes the unit of
comparison.Thesestatisticsarenotinterchangeablemeasuresofsemanticpreservation.
Wrapping further requires the decoding interpretation to be stated.
9.3 Generalizability and Temporal Validity
The historical corpus is an identifiable collection of compact payloads, not a represen-
tative sample of all Windows programs. Its x64 and x86 subsets differ in composition
as well as size. A campaign selected because of earlier failures concentrates on a par-
ticular part of that corpus. Small LLM pilots on one or a few inputs support case-level
observations and require additional evidence for broad conclusions.
Static-scan services change over time. Engine availability, format support, and sig-
natures may differ between a historical submission and a current scan. Even contempo-
raneous raw-file scans do not reproduce full application delivery, loading, or endpoint
execution. Observed verdict fractions are therefore interpreted as properties of the sub-
mission setting and the identified artifacts.

10 Conclusions
TheextendedZonearchitecturemakescode–dataidentificationanexplicitcomponentof
payload rewriting. Its symbolic and heuristic path and its LLM-based alternative feed a
shared deterministic data-handling layer. This separation supports analysis of candidate
quality, reference handling, and downstream functionality as distinct questions.
ThetransformationextensionintroducesaseparateuseofLLMs,withzero-shotand
two-shot conditions and explicit validation and feedback. Assembly wrapping adds an
implementation of an established technique, while the x86 port remains development
work until its architecture-specific assessment is completed. These contributions extend
the conference design beyond its original transformation catalogue and experimental
baseline.
Theassessmentframeworkdistinguishesconstruction,empiricalfunctionality,static
verdicts, similarity, diversity, and cost. Its purpose is to connect each conclusion to the
evidence that can support it. The historical measurements characterize the earlier en-
gine and corpus; completed extensionresults will characterize the newpaths under their
stated configurations. Broader claims about semantic equivalence, unseen inputs, or de-
ployed endpoint products require evidence outside those boundaries.
